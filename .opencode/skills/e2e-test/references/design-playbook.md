# CTB 判别式测试设计手册

本手册是 e2e-test 唯一的设计知识入口。主线只有一条：**每条 testcase 存在的理由，是让某个具体的错误实现失败。** 技术名称、覆盖档位、质量分类都服务于这条主线，不能替代它。

## 0. 何时读哪一节

| 阶段 | 必读 | 产出写入 design.json |
| --- | --- | --- |
| 首次接题 | §1 §2 §3 | `contract`、`mechanisms`、`required_techniques` |
| 推导测试 | §4 §5 §6，题目规定了技术时加 §7，有质量要求时加 §8 | `hypotheses`、`tests` |
| 交付前自检 | §9 | `audit`、`gaps`、`delivery` |
| 收到反馈后 | §10 | `increments`、更新 `hypotheses` |
| 需要读 JAR 时 | §11 | `reference_analysis` |

## 1. 判别三条件：为什么用例多却不命中

一个隐藏错误被某条 testcase 判出，必须同时满足三个条件（借用变异测试的 RIP 模型）：

| 条件 | 含义 | CTB 中最常见的失效方式 |
| --- | --- | --- |
| **R 可达** | 在合法前置下，执行真正走到含错误的那段逻辑 | 前置非法或资源不足，早早被同一个拒绝码挡住；测拒绝路径时同时违反多个守卫，只到达第一个守卫 |
| **I 激发** | 输入落在"错误实现与正确实现行为不同"的点上 | 用典型值：余额 0 时 `>` 与 `>=` 无差别；数量 1 时乘除无差别；只有一个对象时作用域错误无差别；首次操作时累计/重置错误无差别 |
| **P 传播** | 差异被断言观察到 | 只断言返回码前缀；不查状态；拒绝后不检查状态保持；不做后续操作验证效果 |

**工作假设（未经平台证实，按此设计但不当作事实陈述）**：平台的每个 BUG 对应一个被注入错误的程序版本，testcase 在该版本上失败即算命中。在此假设下：

- 判别力 = 让多少种错误版本失败；testcase 数量本身没有价值；
- 一条用例在任意一步失败都会计为命中，所以**中途每一步都断言**能顺带判出前置路径上的错误；
- 一个错误版本只要有一条用例能判出即可，重复判同一错误不增加命中。

所以"堆用例但命中不增"通常是三类系统性问题：R 失效（大量用例卡在同一前置或同一拒绝码）、I 失效（区分值没选对）、P 失效（观察太浅）。另有第四类：**模型缺口**，即整个业务机制从未被建模，自然也没有用例触及。复杂题停在低命中时，要先怀疑第四类。

## 2. 契约卡

目的：在设计任何用例前，弄清"能做什么、能看到什么、怎样算对"。

逐条命令记录：命令/AW 名、参数格式与合法域、全部响应及含义、读写哪些状态、规格出处。另外记录：

- **观察通道**：哪些命令能读出状态（查询、列表、统计、后续操作的成败）。规格说"某接口本身不考"，只代表不为它单独设计用例，**不代表不能用它做辅助观察**，除非规格明确禁止。
- **复位与初态**：tearDown/init 的实际效果；每条用例从什么状态开始。
- **限制**：testcase 数量上限、时间限制、不测范围。"某参数不考"不意味着前置可以用非法值。
- **依据优先级**（`oracle_policy`）：默认以公开规格为断言依据；题目明确写了"冲突时以调测系统为准"，才可在正确环境实测后以其表现为准，并记录条款出处。
- **规格歧义**：同一句话可有两种读法时，列出两种读法；能用正确环境实测区分的就实测（记录为 `basis: reference_observed`），否则不对歧义点下硬断言，记 GAP。

## 3. 机制模型

**机制** = 一组状态变量 + 读写它们的操作 + 操作的守卫（条件）+ 效果（状态写）+ 输出 + 生命周期事件。隐藏错误总是落在某个机制的某个元素上，所以机制清单的完整度直接决定命中上限。

机制卡（写入 `mechanisms[]`，每张卡保持短小）：

```json
{"id": "M3", "name": "按账户累计存款限额", "state": ["deposited[acc]", "balance[acc]"],
 "ops": ["DEP"], "spec_refs": ["§3.2"],
 "guards": [{"id": "M3.G1", "rule": "账户存在", "on_fail": "E001"},
            {"id": "M3.G2", "rule": "1<=amt<=1000", "on_fail": "E002"},
            {"id": "M3.G3", "rule": "deposited+amt<=2000", "on_fail": "E003"}],
 "guard_order": "规格未定义 / §x 定义为 G1>G2>G3",
 "effects": [{"id": "M3.E1", "write": "deposited+=amt; balance+=amt"}],
 "outputs": [{"id": "M3.O1", "what": "成功返回 E000:Success"}],
 "lifecycle": ["INIT 清零", "销户后重开应归零（若规格有销户）"],
 "transitions": []}
```

**找机制的来源**（逐项过一遍，不要只按命令列表）：

1. 名词：每个有状态的实体（账户、订单、玩家、炸弹、板卡、工单……）及其属性；
2. 数字规则：阈值、上限、累计、计数、配额、价格公式、取整；
3. 时间：时钟推进、超时、周期、冷却、过期；
4. 资源：占用/释放、容量、复用；
5. 身份与权限：不同角色/对象能做什么；
6. 批量与列表：多成员操作、部分失败、排序、分页、去重；
7. 状态机：显式状态字段、允许/禁止的转换；
8. 输出：查询结果的字段、顺序、格式、精度。

**完整性交叉核对**（客观、可执行，交付前必做）：

- (a) 规格中出现的每个响应码/错误信息 → 至少对应一个守卫；
- (b) 每个状态变量 → 列出写它的所有操作和读它的所有操作（CRUD 矩阵）；只有写没有读的变量说明缺观察通道，只有读没有写的变量说明漏了某个操作的效果；
- (c) 有可读 JAR 时（§11）：业务类字段 ↔ 状态变量、命令分发 ↔ 操作、字符串常量中的响应码 ↔ 守卫。对不上的项，要么补进模型，要么写一句与业务无关的理由；
- (d) 每个会失败的操作 → 明确"失败后哪些状态必须保持"。

## 4. 故障算子目录

对每个机制元素，问"它最可能怎样被写错"。下表是规格层面的变异算子，覆盖了常见的注入错误形态；新的错误形态可以补充，但要写清楚激发和传播方式。

| 算子 | 作用于 | 典型错误实现 | 激发条件 I | 传播观察 P |
| --- | --- | --- | --- | --- |
| `G-BND` 边界偏移 | 守卫阈值 | `<`↔`<=`、常量 ±1、比较了错误一侧 | 恰在**有效边界**及其 ±1；有效边界包括累计后的边界 | 完整响应 + 边界处状态 |
| `G-DROP` 守卫缺失 | 任一守卫 | 检查被删除 | **只**违反该守卫，其余全部满足 | 应拒绝码 + 状态保持 |
| `G-LOGIC` 条件组合错 | 复合条件 | AND↔OR、漏子条件、取反 | 每个子条件单独翻转结果（独立影响对） | 结果翻转 |
| `G-ORDER` 检查顺序错 | 多守卫同时违反 | 先报了另一个错误 | 同时违反两个守卫——**仅当规格定义了优先级** | 精确响应码 |
| `G-SCOPE` 判定对象错 | 按对象的守卫 | 检查了别的对象/全局值 | ≥2 个对象且取值不对称 | 对象 A 的结果不受 B 影响 |
| `E-MISS` 效果缺失 | 状态写 | 没更新/只更新部分字段 | 任意成功操作 | 查询状态或依赖它的后续操作（L3/L4） |
| `E-CALC` 计算错 | 公式/取值 | 用错变量、常量、取整、单位 | 区分值（§5.1），让常见错误公式得出不同结果 | 完整数值 |
| `E-FAIL` 失败仍写入 | 失败路径 | 拒绝后仍扣减/计数；批量部分提交 | 触发拒绝 | 拒绝后状态完全不变 + 后续正常操作按原状态成功 |
| `E-SCOPE` 写错对象 | 状态写 | 写到别的对象/全局 | ≥2 个对象 | 未操作对象保持不变（L5） |
| `E-ACCUM` 累计/计数错 | 计数、累计、第 N 次 | 不累加、重复累加、不重置、错位 | N−1、N、N+1 次；重置后再来一次 | 第 N 次的行为差异 |
| `L-STALE` 生命周期残留 | 删除/重开/复位/周期翻转 | 旧状态泄漏到新周期或新对象 | 先制造非零状态，再触发生命周期事件 | 新周期/新对象为初值 |
| `S-TRANS` 状态转换错 | 状态机 | 漏转换、多转换、目标状态错、非法转换被允许 | 每个状态下尝试合法与非法操作 | 转换后能做/不能做什么 |
| `T-TIME` 时间处理错 | 超时/周期/冷却 | 边界时刻错、时间不推进、按错时钟 | 刚好到期、差 1 个单位 | 到期前后的行为 |
| `R-LEAK` 资源不释放 | 占用/释放 | 释放后容量不恢复、重复释放 | 用满 → 释放 → 再用满 | 释放后可再次占用到满额 |
| `O-FMT` 输出错 | 查询/列表 | 字段/顺序/并列排序/精度/漏项 | 多条记录、并列值、需要排序的数据 | 完整输出对比 |
| `O-CODE` 错误码映射错 | 拒绝路径 | 返回了别的错误码 | 每种拒绝各触发一次 | **完整**响应码，不只断言前缀 |

使用规则：

- 每个机制元素至少过一遍相关算子；判定不适用时可以不建假设，但交付前 `check-design` 会列出未被任何假设指向的元素，届时逐个给出理由或补上；
- 一个假设 = `{target 元素, operator, fault 描述, reach, infect, propagate}`，写入 `hypotheses[]`；
- 优先级：核心业务成功路径上的 `E-*`、每个守卫的 `G-DROP/G-BND`、拒绝路径的 `E-FAIL` 为 P0；交互类算子（`G-SCOPE/E-SCOPE/E-ACCUM/L-STALE/S-TRANS`）在规则存在相应结构时也是 P0；其余按风险判 P1/P2。

## 5. 区分值与观察阶梯

### 5.1 区分值

选数据前做一次**两错检验**：写下这个元素最可能的两种错误实现，把用例数据代入，确认它们与正确实现的输出不同。相同就换数据。常用规则：

- 避开恒等值：0、1、相等的两个量、默认值、初值；
- 数值让常见错误公式分叉：例如单价 3、数量 7，不用 1×1；
- 边界取**有效边界**：考虑累计、余量、已占用后的实际阈值，而不是参数域边界；
- 多对象取值不对称：A 满额、B 未满；A 有状态、B 为初值；
- 第 N 次行为：至少覆盖 N−1、N、N+1，并在重置后再走一次；
- 有排序/并列规则时，构造并列与逆序数据。

### 5.2 观察阶梯

| 级别 | 观察内容 |
| --- | --- |
| L1 | 返回码 |
| L2 | 完整返回内容（码 + 文本/数值/列表） |
| L3 | 通过查询读出相关状态 |
| L4 | 依赖该状态的后续操作（能否成功、结果数值） |
| L5 | 未被操作的对象/字段保持不变 |

最低要求：`E-*` 类假设需要 L3 或 L4；拒绝类假设需要 L2 + 状态保持（L3/L4）；作用域类假设需要 L5。规格定义了输出格式时，按完整内容比较，不做模糊匹配。

## 6. 组装判别用例

**故事结构**：构造（每一步都断言成功）→ 激发动作 → 按阶梯观察 → 必要时做后续操作验证能力仍正常。

- **前置每步都断言**：前置失败会被立刻暴露（在正确环境不会出现），也能在错误版本上顺带判出前置路径的错误；不要丢弃 AW 返回值；
- **单故障隔离**：测某个守卫的拒绝时，只让这一个守卫被违反；
- **相容合并**：同一机制、或确有业务关联的多个假设可以放进一条连续轨迹，但每个假设都要有自己的观察点；不相关机制的假设分开，便于增量诊断时知道哪条用例对应哪个机制；
- **长轨迹的使用条件**：状态/历史/周期耦合时才用，并说明每段前置的作用；长度本身不是价值；
- **独立性**：每条用例从公开初态起步，不依赖其他用例的执行顺序；
- **登记**：每条 testcase 都登记到 `tests{}`，写明对应假设；没有对应假设的用例说明不了自己的价值。

**反模式**（审计时逐条查）：只断言返回码前缀；丢弃前置返回值；同一前置下只换数值堆数量；同时违反多个守卫；在零状态上测扣减类规则；单对象测隔离；只查询不做后续操作；用 subTest/循环掩盖意图；为通过而放宽断言。

## 7. 题目规定的设计技术

题目若规定了技术及档位，它们是**合规下限**；判别假设是**命中来源**；两者复用同一批用例。术语以题目原文为准；下表只是常见含义，题目定义不同时按题目原文执行，定义不明确时 `definition: unconfirmed`，不得标为已达成。

| 常见缩写 | 覆盖单元 | 通常由哪些算子自然产生 |
| --- | --- | --- |
| 等价类 | 每个处理方式不同的有效/无效类至少一个代表 | `G-DROP`、`O-CODE`、`E-CALC` |
| 边界值 | 每个边界的 on/off 点（含累计边界） | `G-BND`、`E-ACCUM` |
| DTT 判定表 | 每个可行规则列（条件组合 → 动作） | `G-LOGIC`、`O-CODE`；动作要断言效果 |
| DPT/条件判定类 | 按题目档位：判定结果/条件取值/独立影响对 | `G-LOGIC` |
| DCoT 数据组合 | 按档位组合多参数的数据类（如两两组合） | `E-CALC`、`G-SCOPE` |
| DCyt 数据生命周期 | 每个数据实体的创建-读取-使用-修改-删除及跨功能一致性 | `E-MISS`、`L-STALE`、`R-LEAK` |
| STT 状态转换 | 按档位：状态/转换/N-switch 转换序列，须在同一连续轨迹中完成 | `S-TRANS` |
| PCT 流程路径 | 按档位的路径/路径组合 | `S-TRANS`、`E-FAIL` |

记录方式：`required_techniques[]` 写原文出处、档位、覆盖单元清单、对应 testcase（`evidence_tests`）。只写技术名、不列单元和证据，不算达成。

## 8. 质量目标

功能、安全、可靠性、性能四类只在**本题规格/接口确实支持**时设计，依据写入 `quality_applicability`。平台存在某类 BUG 统计，不能作为为本题发明权限、故障注入、并发或性能阈值的理由。

- 安全：规格存在身份、权限、越权、输入滥用规则时，用 `G-DROP/G-SCOPE` 针对保护性守卫；
- 可靠性：失败后继续、恢复、资源释放、反复操作。对应 `E-FAIL`、`R-LEAK`、`L-STALE`，以及"恢复后做一次真实改变状态的业务操作"；
- 性能：只有规格给出指标或阈值时才断言，写清测量对象、窗口、负载与依据。按 §1 的工作假设，导致变慢的错误只有显式时间断言或用例超时才能判出；没有依据时记 GAP，不自定阈值。

## 9. 判别审计（首轮交付前必做，增量轮对改动部分必做）

| 检查 | 方法 | 不通过时 |
| --- | --- | --- |
| A 可达 | `trace-report`：`stuck_on_same_rejection` 为空；`expected_codes_never_observed` 中每个码都有理由（或已补用例）；P0 假设目标步骤的实际响应符合预期 | 修前置，不新增用例 |
| B 激发 | 每个假设的 `infect` 写明两错检验结果 | 换区分值 |
| C 传播 | `lint` 无 `unobserved_aw_call`（或逐条说明）；`E-*` 假设达到 L3/L4 | 补观察 |
| D 冗余 | `identical_trace_groups` 中的组要么有不同断言，要么合并 | 合并或删除，并在 `increments` 记录理由 |
| E 模型 | `check-design`：每个机制都有假设，未被指向的元素有理由；§3 的 (a)–(d) 交叉核对已做 | 补机制/元素 |
| F 技术 | 规定技术的单元全部有 `evidence_tests`，且定义已确认 | 补用例或记 GAP |

首轮可以交付的条件：A–F 无未处理项（或已转成有依据的 GAP）、P0 假设全部 `verified` 或 `gap`、当前版本已真实验证通过。

## 10. 增量诊断（收到平台反馈后）

输入是 loop 给的本题反馈摘要：每条 testcase 的 NEW/REPEAT/MISS/UNKNOWN 分类、命中的 BUG 标识（不透明令牌，只用来判断两条用例是否命中同一个 BUG）、已确认的分类汇总。

1. **命中热图**：把 NEW/REPEAT 用例经 `tests{}` 映射到假设，再映射到机制，把机制分为三类：*已命中*、*有用例但未命中*、*无用例*；
2. **无用例的机制或元素 → 最高优先**：说明存在模型缺口，回到 §3 的交叉核对（尤其是响应码和 CRUD 矩阵），先补模型，再推导假设；
3. **有用例但未命中 → 先修 R/I/P，再考虑新增**：逐条用例对照轨迹检查是否真的到达（R）、两错检验是否成立（I）、观察级别是否足够（P）。修好比新增更有价值；
4. **已命中的机制 → 往交互类算子推进**：在该机制上补 `G-SCOPE/E-ACCUM/L-STALE/S-TRANS` 等尚未覆盖的格子；不因为已命中就假定那里还有更多错误；
5. **分类汇总**的唯一用途：提示复查 §8 的适用性依据。不能据此在没有规格依据时新建场景；
6. **UNKNOWN 不等于未命中**，MISS 不等于没有价值（可能是该机制本来就没有注入错误），REPEAT 不等于冗余（可能同时守护多个错误）。

**合格的增量**（写入 `increments[]`）至少包含以下一项：机制×算子矩阵中的新格子、一条用例的 R/I/P 修复、一次模型更正。每项都要写"旧用例为什么判不出"。只换数据、仍落在同一格子里的改动不算增量。拿不出合格增量时，如实告诉 loop `no_new_hypothesis`，不要硬凑。

**归因要谨慎**：长轨迹命中只说明这条轨迹整体能判出某个错误，不说明哪一步是必要的。

## 11. 本地正确 JAR 的使用

允许：`jar tf` 列类、`javap -p` 看签名、环境里已有反编译器时定点反编译。用来确认命令分发、守卫顺序、状态字段、响应码常量、复位行为、时间处理，也就是 §3 交叉核对 (c) 的输入。

- 断言依据仍是规格；JAR 只在 `oracle_policy` 允许时、并经正确环境实测后，才用来解决歧义；
- 不解码、不启用 JAR 中与业务无关的开关或加密标记，不用 JAR 猜测隐藏错误的位置；
- 可选的诊断手段：环境里已有 JaCoCo agent 时，可在 `.ctb/tmp/` 下用 `JAVA_TOOL_OPTIONS=-javaagent:...` 跑一次诊断，查看命令处理类中从未执行的分支，作为 R 缺口的线索。诊断运行不能替代正式验证（正式验证不带 agent），也不改动任何只读文件。
- 结论写入 `reference_analysis`（读了什么、对应哪些机制元素、哪些仍不确定）。
